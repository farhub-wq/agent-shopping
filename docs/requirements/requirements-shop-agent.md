# shop-agent 需求分析（V1：可上线 MVP）

> 状态：关键假设已于 2026-11-06 确认（见 5.2 假设表），基线数值对齐 [system-design.md](../design/system-design.md) 修订版（2026-11-06）。
> 依据文档：`README.md`、`docs/ARCHITECTURE.md`、`docs/PUBLIC-SOLUTION.md`、`docs/RUNBOOK.md`、当前代码与测试。
> 定位：从“工程参考实现”转向“可真实上线的最小电商”，保留现有架构，不推倒重来。

---

## 1. 问题陈述（不含解决方案）

**谁有这个问题**
- 自营中小电商的经营者：SKU 数千、日订单数百到两千、运营/客服 1–5 人，没有专职后端团队。
- 维护这套系统的开发者：需要在不引入大团队的前提下，保证不超卖、订单状态可追、客服 Agent 不越权。

**问题是什么**
1. 现有开源商城 Demo 多为单库 CRUD，无法回答“并发下会不会超卖”“事件丢了订单会不会卡住”。
2. 现有 Agent 框架只解决“模型怎么调工具”，不解决“工具能不能被调、调用后能不能被审计”。
3. 两者割裂导致上线时要重新拼装：库存与订单的一致性、Agent 的权限边界都要从零补。
4. 缺少可上线的运营闭环：支付回调、退款到账、发货签收、异常告警、备份恢复。

**不解决会怎样**
- 超卖造成赔付与客诉；订单状态卡死需要人工改库；Agent 误退款造成资损；出问题无法定位与回滚。
- 业务方只能继续用 Excel + 人工对账，规模一涨就不可控。

**今天的替代做法**
- 购买 SaaS（数据与流程受制于人）、用开源 Demo 二次开发（一致性缺陷隐藏深）、或纯人工运营（无法扩展）。

**需求成立的前提（待验证）**
- 单租户自营，不是 SaaS 多租户平台；
- 支付走第三方托管收银台/聚合支付，不自建清结算；
- 部署在单云厂商，允许 Docker Compose 或轻量 K8s；
- 团队 ≤ 3 人，无 7×24 运维值班。

## 2. 用户与场景（Jobs-to-be-Done）

| 角色 | 场景 | 想要 | 以便 |
|---|---|---|---|
| 顾客 | 想买一件商品 | 看到真实可售库存与价格，一次下单成功 | 不出现“下单后告知缺货” |
| 顾客 | 支付后等收货 | 知道订单当前状态与预计时间 | 不用反复找客服 |
| 顾客 | 商品有问题 | 提交售后并在承诺时限内拿到结论与退款 | 不必反复催 |
| 运营 | 每天处理订单 | 看到待发货、超时、待审批清单 | 不漏单、不超时 |
| 运营 | 处理退款 | 有风险提示与审批记录 | 不被误退、可追责 |
| 客服（Agent） | 回答库存/订单问题 | 只读查询 + 提议售后 | 不越权、不编造 |
| 开发者 | 上线与排障 | 一键部署、指标与日志、可回滚 | 故障分钟级定位 |

> “五个具体用户”尚未落实：当前假设为 1 名经营者 + 2 名运营 + 1 名客服 + 自己作为开发者。若与实际不符，第 7 节的优先级需重排。

## 3. 需求层级（Need Hierarchy）

**业务存续（必须）**
- 不超卖、不重复收款、退款金额正确且可对账。
- 订单状态与履约、售后事实一致。

**顾客体验（必须）**
- 商品可浏览、库存可信、下单与支付可完成、进度可见、售后有结论。

**运营效率（必须）**
- 待办清单（待发货 / SLA 超时 / 待审批 / 异常订单）。
- 所有人工动作留痕，可按订单/用户检索。

**Agent 安全（必须）**
- 只读能力默认开放；写操作与不可逆动作必须审批；每次运行可回放证据。
- 模型/供应商不可用时业务不阻塞。

**增长（可延后）**
- 优惠券、搜索推荐、通知、报表、多仓、多币种、多租户。

| 状态 | 症状 | 本项目现状 | 结论 |

| RA1 方案先行 | 文档大量描述实现（Lua、Outbox、Trust tier） | `ARCHITECTURE.md` 以“怎么做”为主，需求条目未编号、无验收标准 | **主要问题**：需把实现转成可验证需求 |
| RA2 需求模糊 | “可上线 MVP”没有定义完成标准 | 只有 RUNBOOK 的操作步骤，无 Given/When/Then | 需补 V1 验收基线 |
| RA3 隐藏约束 | 支付渠道、部署环境、合规地域未定 | “已知边界”写清了技术限制，但业务约束缺失 | 需假设地图（第 5 节） |
| RA4 范围蔓延 | 文档提到多租户、跨境、虚拟商品等扩展 | 属于“替换点”，不是 V1 需求 | 明确划入 Won't 或 Should |
| RA5 需求已验证 | — | 尚未达到 | 待关键假设确认后达标 |

**文档已有的优点（保留）**
- 数据所有权、事件契约、安全边界写得具体，可直接转成约束。
- 三个难点的实现与测试（34 passed）已具备可验证基础。

**文档缺口**
- 无真实账号体系需求（当前 token 接口按请求体签发角色，等于可自选权限）。
- 支付仅有 mock，无回调验签、幂等、对账需求。
- 无通知、报表、可观测性、备份恢复、容量与 SLO 需求。
- 无“上线准入”清单，也没有验收数据（并发、压测、故障演练）。

## 5. 约束清单与假设地图

### 5.1 事实（代码/文档可证）

| # | 事实 | 影响 |
|---|---|---|
| C1 | Python 3.11 + FastAPI + SQLAlchemy async；MySQL 8 + MongoDB 7 + Redis 7 | 技术栈不变，需求不能要求更换运行时 |
| C2 | 五业务服务各自独立库，跨服务只走 HTTP / 事件 | 需求不得要求跨库 join |
| C3 | 状态变更必须走 `resolve_target`，事件必须走 outbox | 新需求不得绕过 |
| C4 | 库存扣减必须走 Lua 脚本 | 任何促销/秒杀需求都复用该路径 |
| C5 | 当前单镜像多入口（`SERVICE_NAME`）用于本地启动 | 上线需拆独立部署单元 |
| C6 | 本地沙箱不是安全边界，Docker 沙箱才有隔离 | Agent 执行类需求必须要求 Docker |
| C7 | 当前测试 34 passed；前端可构建 | 任何新需求必须补对应测试 |
| C8 | 当前无真实注册/登录、无真实支付、无指标与告警 | 这些是 V1 的硬缺口 |

### 5.2 假设（未验证，必须确认）

| # | 假设 | 若不成立的影响 | 验证方式 |
|---|---|---|---|
| A1 | 单租户，日订单 ≤ 3 万，SKU ≤ 5 万 | 架构与索引需重做，V1 范围扩大 | ✅ 已确认（2026-11-06） |
| A2 | 浏览峰值 300 QPS，下单峰值 30 TPS | 性能目标失效 | ✅ 已确认（2026-11-06） |
| A3 | 支付用第三方聚合/托管收银台 | 需自建对账、PCI 范围扩大 | 与支付渠道确认 |
| A4 | 部署单云，Docker Compose 起步 | 若要求 K8s/多可用区，需补部署需求 | 运维环境确认 |
| A5 | 退款原路退回，T+1 到账 | 若需即时到账，需接资金通道 | 支付渠道确认 |
| A6 | 数据保留：订单 5 年、日志 30 天；PII V1 明文存储 + 日志脱敏，字段级加密留 Should | 合规成本变化 | ✅ 已修订（2026-11-06） |
| A7 | 客服 Agent 面向真实顾客，模型供应商可选 | 成本与内容安全要求变化 | 产品确认 |
| A8 | 无需发票、优惠券、多币种 | 范围可缩小 | 业务确认 |

### 5.3 项目杀手（pre-mortem）

1. 支付回调验签/幂等没做好 → 重复发货或漏单（已发生概率高）。
2. 账号体系仍可自选角色 → 任意用户可调用运营接口。
3. 无指标与告警 → 超卖/卡单只能靠客诉发现。
4. Agent 提示注入绕过工具策略 → 越权查询他人订单或触发退款提案。
5. 无备份恢复 → 数据库故障即业务停摆。

## 6. 范围定义（V1）

### 6.1 Must（没有就不能上线）

- 账号注册/登录、角色与权限校验（顾客 / 运营 / 管理员）。
- 商品浏览、真实可售库存展示。
- 下单幂等、库存预占与超时释放、支付（第三方沙箱/生产）、支付回调验签与幂等、迟到支付自动退款。
- 管理员库存管理：入库/盘点调整（幂等、审计留痕）。
- 库存对账任务（Redis 数字 vs DB，5 分钟粒度，差异以 DB 为准重建并告警）。
- 履约发货/签收、订单状态轨迹可查。
- 售后申请、审批、退款发起与结果回写。
- 运营后台待办清单（待发货 / 超时 / 待审批）与操作审计。
- 客服 Agent（只读查询 + 售后提议），不可逆动作强制审批，运行证据可查。
- 可观测性：错误率、下单/支付成功率、库存预占失败率、订单卡单告警。
- 部署与回滚：独立镜像、环境配置、数据库迁移、备份恢复演练。

### 6.2 Should（上线后 1–2 个迭代）

- 订单状态通知（短信/邮件/站内信）。
- 运营报表：GMV、订单量、售后率、Agent 拦截率。
- 商品搜索与简单筛选。

### 6.3 Could（有明确触发条件再做）

- 优惠券/满减（触发：客单价运营需求出现）。
- 多仓/门店自提（触发：单仓履约超时率 > 5%）。
- 多币种/跨境（触发：确定跨境业务）。
- 多租户 SaaS（触发：确定对外售卖）。

### 6.4 Won't（V1 明确不做）

- 自建支付清结算、发票系统、推荐算法、直播带货、复杂促销引擎。
- Agent 自动执行退款/改价/改地址等不可逆动作。
- 多租户隔离与租户级计费。

### 6.5 V1 完成定义（Exit Criteria）

1. 上述 Must 全部通过验收用例；
2. 压测证明不超卖（见 NFR-01）；
3. 支付回调重复投递 100 次不重复发货；
4. 故障演练：kill 一个服务后 5 分钟内可恢复或降级；
5. 备份恢复演练：RPO ≤ 15 分钟、RTO ≤ 4h；
6. Agent 越权用例全部被拒绝或转审批；
7. 上线检查单（配置、密钥、迁移、告警）全部勾选。

## 7. 验证后的需求（FR / NFR）

> 状态列：✅ 已实现 · ⚠️ 部分实现/需加固 · ❌ 缺失

### 7.1 功能需求

| ID | 需求（不含实现） | 验收标准（Given / When / Then） | 现状 |
|---|---|---|---|
| FR-01 | 顾客可注册并登录，身份由系统校验而非自报 | Given 未登录用户，When 提交有效凭证，Then 获得有时效的会话；无效凭证返回 401 且不签发 | ❌ |
| FR-02 | 角色权限不可被客户端伪造 | Given 顾客 token，When 调用运营接口，Then 403；Given 运营 token，Then 允许并记录操作人 | ⚠️ |
| FR-03 | 顾客能看到真实可售库存 | Given 库存 0，When 浏览商品，Then 显示缺货且不可下单 | ✅ |
| FR-04 | 下单不超卖，失败可回滚 | Given 库存 1，When 并发 100 次下单，Then 成功 1 次、其余 409，库存不为负 | ⚠️ 需压测 |
| FR-05 | 同一幂等键重复提交只产生一个订单 | Given 同一 Idempotency-Key，When 重复提交 10 次，Then 返回同一订单且库存只扣一次 | ✅ |
| FR-06 | 支付结果以渠道回调为准，且回调可重复 | Given 渠道重复回调同一支付单，When 处理，Then 订单只推进一次、只发一次履约事件 | ❌ |
| FR-07 | 支付金额与订单金额可对账 | Given 日终，When 生成对账结果，Then 差异单可列出并可人工处理 | ❌ |
| FR-08 | 发货与签收可被顾客看到 | Given 已支付订单，When 运营发货，Then 订单进入已发货并展示运单号；签收后进入已完成 | ✅ |
| FR-09 | 售后申请在承诺时限内得到结论 | Given 售后单，When 超过 SLA 未处理，Then 进入超时清单并告警 | ⚠️ |
| FR-10 | 退款金额与审批记录一致且可追溯 | Given 审批通过金额 X，When 退款完成，Then 退款金额=X，记录审批人/时间/备注 | ⚠️ 实际退款未接入 |
| FR-11 | 运营动作全部留痕 | Given 任一运营写操作，When 完成后，Then 可查到操作人、对象、时间、前后状态 | ⚠️ 仅 Redis 短保留 |
| FR-12 | Agent 只能做被授权的事 | Given 顾客请求退款，When Agent 处理，Then 只返回待审批，不执行退款 | ✅ |
| FR-13 | 每次 Agent 运行可回放 | Given 一次运行，When 查询证据，Then 返回工具调用、结果、拒绝项与摘要校验值 | ✅ |
| FR-14 | 模型不可用时客服仍可用 | Given 模型不可达，When 顾客提问，Then 返回确定性答复或明确降级提示，不返回 5xx | ✅ |
| FR-15 | 订单状态变化可通知顾客（Should） | Given 支付/发货/退款完成，When 事件发生，Then 顾客收到一次通知 | ❌ |
| FR-16 | 运营可查看核心经营指标（Should） | Given 选定日期，When 打开报表，Then 显示 GMV、订单数、售后率 | ❌ |

### 7.2 非功能需求

| ID | 需求 | 验收标准 | 现状 |
|---|---|---|---|
| NFR-01 | 不超卖 | 库存 100，200 并发下单，成功 ≤100，最终库存 ≥0，DB 与 Redis 对账一致 | ⚠️ 需压测 |
| NFR-02 | 订单状态一致性 | 注入重复/乱序事件各 50 次，订单状态与轨迹仍单调正确，无重复履约单 | ⚠️ 需故障测试 |
| NFR-03 | 性能 | 商品列表 P95 < 300ms、下单 P95 < 800ms（300 QPS / 30 TPS 下；压测按 2 倍余量 600 QPS / 60 TPS 验收） | ❌ 未测 |
| NFR-04 | 可用性 | 月度可用性 ≥ 99.5%；单实例故障后 5 分钟内恢复或降级 | ❌ |
| NFR-05 | 安全 | 无自选角色；密钥不入库不入日志；运营接口强制鉴权；PII 传输与存储加密；依赖漏洞扫描通过 | ⚠️ |
| NFR-06 | 可观测性 | 下单/支付成功率、错误率、卡单数、Agent 拒绝率有指标；阈值告警可送达 | ❌ |
| NFR-07 | 备份恢复 | 每日备份，RPO ≤ 15 分钟，RTO ≤ 4h，每季度演练 | ❌ |
| NFR-08 | 数据合规 | 订单保留 5 年、日志 30 天；用户可申请删除非必要 PII；退款记录不可删除 | ❌ |
| NFR-09 | 部署与回滚 | 独立镜像可部署；数据库迁移可前滚可回滚；发版 30 分钟内可回退 | ⚠️ |
| NFR-10 | Agent 成本与安全 | 单次会话 token/工具调用有上限；提示注入用例无法越过工具策略；不可逆动作 100% 转审批 | ⚠️ |
| NFR-11 | 可维护性 | 新增一条业务规则不改跨服务代码；关键路径有自动化测试；lint 与构建全绿 | ✅ |

## 8. 差距与优先级

**P0（上线阻断，必须先做）**
1. 真实账号体系与角色校验（FR-01/02、NFR-05）——当前可自选角色，属于提权漏洞。
2. 支付接入、回调验签与幂等、对账（FR-06/07、NFR-02）。
3. 可观测性与告警、备份恢复（NFR-06/07）。
4. 压测与故障演练，证明不超卖与状态一致（NFR-01/02/03）。

**P1（上线后首个迭代）**
5. 通知与报表（FR-15/16）。
6. 审计持久化（FR-11）。
7. Agent 成本上限与提示注入回归（NFR-10）。

**P2（按触发条件）**
8. 搜索、优惠券、多仓、多租户。

## 9. 待决策问题（需要业务回答）

1. 支付渠道选谁？是否托管收银台？退款是原路退回还是余额？
2. 部署环境：单机 Compose、云服务器多实例，还是 K8s？是否有域名/HTTPS/备案要求？

5. 客服 Agent 是否直接面向真实顾客？模型供应商与月度成本上限？
6. V1 是否接受“仅支持全额退款、单一仓、单一币种”？
7. 运营团队人数与值班方式：告警发到哪里、谁处理？
